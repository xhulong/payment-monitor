## 1. 当前结论

目前已经完成的是“**本地通知监听 + 服务端支付事件中心 Phase 1**”，还不是完整的免签支付系统。

现有链路：

```text
Android 本地监听、解析、Room 保存

测试夹具 → 设备配对 → HMAC 心跳 → 支付事件上传
              ↓
      PostgreSQL 事件中心
              ↓
       Vue 管理端查询
```

实际缺口位于 Android 与服务端之间：Android App 当前没有网络权限、配对页面、设备密钥安全存储、HMAC 客户端、心跳和离线上传队列。因此真实微信、支付宝通知还不能自动进入服务端。

推荐顺序：

```text
先补稳现有协议
  → 完成 Android 到服务端闭环
  → 真实设备通知联调
  → 管理端与运维补强
  → 订单、二维码和到账匹配
  → 可靠 Webhook
  → 多商户与生产部署
```

不建议现在直接开发订单匹配。否则 App 上传协议、时间格式、事件状态和隐私策略变化后会导致订单模块返工。

## 3. 需要优先修复的关键问题

### P0-1：Android 尚未接入服务端

需要增加：

- `INTERNET`、网络状态权限；
- 服务器地址配置；
- 输入或扫描配对二维码；
- 调用 `/api/v1/devices/pair`；
- Android Keystore 保存 `deviceId` 和 `deviceSecret`；
- HMAC 请求签名；
- 心跳、服务端配置拉取；
- 支付事件批量上传；
- 服务端返回 `accepted/duplicates` 后更新本地状态。

### P0-2：Room 当前会无条件删除 500 条以外的旧数据

联网后，如果待上传事件超过 500 条，当前保留策略可能删除尚未同步的数据。

数据库升级后必须调整为：

```text
PENDING/RETRYING 事件永不因普通保留策略删除
UPLOADED 事件只保留最近 500 条或指定天数
队列过大时显示告警，而不是静默丢弃
```

### P0-3：缺少统一时间契约

后端 DTO 当前使用 `LocalDateTime`，无法表达时区。Android 使用 Epoch 毫秒。

建议在进入 App 联调前冻结为：

```text
API 时间：UTC ISO-8601，例如 2026-07-16T06:30:00Z
数据库：统一保存 UTC
界面：按用户/商户时区显示
```

后端 DTO 改用 `Instant` 或 `OffsetDateTime`。历史数据库字段可继续使用 `timestamp`，但应用层必须明确转换规则。

### P0-4：配对二维码只包含 8 位数字

手机无法通过二维码获知服务端地址，且真机中的 `localhost` 指向手机自身。

建议二维码内容：

```json
{
  "schema": 1,
  "serverUrl": "https://HOST",
  "pairingCode": "12345678"
}
```

二维码不能包含 `deviceSecret`。本地 Debug 可允许局域网 HTTP；Release 默认只允许 HTTPS。

### P0-5：缺少真实微信、支付宝通知样本

目前解析测试主要来自参考 APK 规则和四类构造样本。必须在真实设备收集：

- 微信收款助手；
- 微信收款商业版；
- 微信店员收款；
- 微信付款；
- 支付宝个人收款；
- 支付宝店员通；
- 支付宝付款；
- 金额缺失、合并通知、通知更新和重复通知。

完整原文只用于内部调试，并应支持脱敏、导出后删除。

## 4. 后端尚未完善的功能

### 4.1 设备与凭据

- 设备名称修改；
- 设备重新配对和密钥轮换；
- 密钥版本升级；
- 配对码过期数据清理；
- 配对码生成冲突自动重试；
- 心跳历史、最后上传时间、待处理数量；
- App 版本过旧提示；
- 设备离线告警；
- 设备被吊销后返回稳定的错误码，App 进入“需要重新配对”状态。

### 4.2 支付事件

- `RECEIVED/REVIEWED/IGNORED/MATCHED/CONFLICT` 状态流转；
- 人工标记误报、确认收入和修正金额；
- 规则升级后的重新解析；
- 按金额范围、通知文本、设备名称查询；
- CSV/Excel 导出；
- 原始通知字段脱敏和单独权限；
- 原始数据保留时间与自动清理；
- 跨设备重复识别。

当前唯一约束只覆盖：

```text
(merchant_id, client_event_id)
```

不同设备收到同一笔通知时仍可能产生两条事件。建议先增加“疑似重复”标记，不直接建立过强唯一约束：

```text
merchant + platform + direction + amount + rawHash + 时间窗口
```

### 4.3 商户和权限

- 当前管理 API 固定使用默认商户；
- 没有商户管理页面；
- 没有商户级数据隔离；
- 新增菜单未为普通角色自动授权；
- 原始通知、设备密钥操作应使用更细权限；
- 需要审计配对、禁用、吊销、查看原文和人工修正操作。

### 4.4 统计

当前仪表盘只有当日事件数量。后续应增加：

- 收入金额合计；
- 微信/支付宝金额占比；
- 小时/日趋势；
- 解析失败率；
- 重复率；
- 设备在线率；
- 上传延迟；
- 未匹配、冲突和 Webhook 失败数量。

## 5. Android 尚未完善的功能

### 5.1 配对与安全存储

- 配对页面、扫码、手工输入；
- 服务器地址合法性检查；
- Debug HTTP 与 Release HTTPS 分离；
- Keystore 加密保存凭据；
- 清除配对和重新配对；
- 禁止日志输出 Token、Secret、完整签名；
- 服务端证书错误和网络错误提示。

### 5.2 本地上传队列

Room 建议升级到 V2，增加：

```text
clientEventId
parserVersion
notificationKeyHash
rawHash
uploadStatus
attemptCount
nextAttemptAt
lastAttemptAt
uploadedAt
lastErrorCode
lastErrorMessage
```

上传状态：

```text
PENDING
UPLOADING
RETRYING
UPLOADED
REJECTED
```

客户端处理规则：

| 服务端结果 | App 行为 |
| --- | --- |
| accepted | 标记 `UPLOADED` |
| duplicates | 标记 `UPLOADED` |
| rejected | 标记 `REJECTED`，显示原因 |
| HTTP 401 | 校准时钟；仍失败则要求重新配对 |
| HTTP 429 | 按服务端提示退避 |
| HTTP 5xx/断网 | 指数退避重试 |

### 5.3 心跳和任务调度

- 前台服务运行时使用协程按服务端配置心跳；
- WorkManager 负责断网恢复和待上传事件补偿；
- 不使用 WorkManager 实现 60 秒心跳，因为周期任务最小间隔不适合；
- 手机重启后不自动监听，但保留未上传事件，并在用户下次启动时继续上传；
- 记录服务端时间偏移，避免手机时间不准导致 HMAC 被拒绝。

### 5.4 UI

- 服务器连接状态；
- 已配对设备信息；
- 最后心跳、最后同步时间；
- 待上传、失败、已上传数量；
- 单条事件上传状态和手动重试；
- 网络、签名、设备被禁用等错误提示；
- 通知权限、通知监听权限、电池限制的分步检查；
- 开始监听前同时检查通知使用权和通知权限。

## 8. 分阶段实施计划

### 阶段 A：协议与事件中心加固

预计：2～3 个开发日。

任务：

1. 时间字段统一为 UTC；
2. 定义稳定错误码；
3. 配对响应增加 `serverTime`、协议版本；
4. 配对二维码增加 `serverUrl`；
5. 增加密钥版本字段和重新配对规则；
6. 增加 HMAC、时间偏差、批量上限和 Flyway 集成测试；
7. 增加普通角色菜单授权验证。

验收：

- OpenAPI 和 Android DTO 固定；
- Android 可以只根据文档完成签名；
- 错误码能区分重试、拒绝和重新配对；
- PostgreSQL/Redis Testcontainers 测试通过。

### 阶段 B：Android 到服务端闭环

预计：5～8 个开发日。

任务：

1. 增加网络权限和 API 客户端；
2. 增加服务端地址、扫码和配对页面；
3. Keystore 保存设备凭据；
4. 实现 HMAC 拦截器；
5. Room V2 上传队列；
6. 批量上传与逐条 ACK；
7. 前台心跳；
8. WorkManager 离线补传；
9. 同步状态和错误页面。

验收：

- Debug 样本可以从 App 自动进入服务端；
- 飞行模式产生事件，恢复网络后自动上传；
- App 进程被杀后待上传事件仍存在；
- duplicate 响应不会反复重试；
- 设备禁用后 App 明确显示需要处理。

### 阶段 C：真实支付通知联调

预计：3～5 个开发日，依赖真实微信/支付宝设备。

任务：

1. 建立脱敏样本库；
2. 覆盖微信店员收款和商业版；
3. 覆盖支付宝店员通；
4. 测试合并通知、通知更新、重复通知；
5. 调整金额和方向评分；
6. 增加解析器版本；
7. 增加误报、漏报统计。

验收：

- 至少覆盖每个平台 20 条以上真实脱敏样本；
- 收款样本不被识别为付款；
- 订单号、时间、尾号不被误认为金额；
- 金额缺失和方向冲突事件仍能上传并复核。

### 阶段 D：管理和运维补强

预计：4～6 个开发日。

任务：

- 设备详情、同步状态和心跳历史；
- 事件审核、修正、忽略、导出；
- 统计趋势；
- 原始数据权限和脱敏；
- 健康检查、备份脚本、日志滚动；
- CI 和 Testcontainers；
- 完整 Docker 部署样例。

验收：

- 非管理员不能查看原始通知；
- 数据库可备份并恢复；
- 服务异常、设备离线和上传积压可被发现；
- 提交代码后自动执行三端基础检查。

### 阶段 E：订单、二维码和到账匹配

预计：8～12 个开发日。

任务：

- 商户订单；
- 整数分金额；
- 金额预留和并发唯一约束；
- 二维码资产；
- 支付页和订单超时；
- 收入事件自动匹配；
- 未匹配、冲突和人工补单；
- 匹配审计。

验收：

- 只有收入且金额有效的事件可以支付订单；
- 并发创建订单时金额不冲突；
- 一个事件只能匹配一个订单；
- 多候选事件进入冲突列表；
- 重复通知不能导致重复支付。

### 阶段 F：可靠 Webhook

预计：5～8 个开发日。

任务：

- Webhook endpoint；
- Outbox；
- HMAC 签名；
- 指数退避；
- 投递日志；
- 手动重试；
- SSRF、TLS 和响应大小限制。

验收：

- Webhook 接收方离线时订单仍保持已支付；
- 后端重启后继续投递；
- 相同 `deliveryId` 可由商户幂等处理；
- 管理端可查看每次投递结果。

### 阶段 G：多商户与生产化

预计：7～10 个开发日。

任务：

- 商户管理；
- 商户 API Key/HMAC；
- 商户级数据隔离；
- 多角色；
- 多设备重复识别；
- 生产域名、TLS、备份、监控和发布流程；
- 可选旧接口兼容。

验收：

- 商户之间无法读取彼此数据；
- 每个商户独立设备、二维码和 Webhook；
- 生产环境不使用默认密码或本地示例密钥；
- 完成升级、回滚和恢复演练。

## 9. 推荐的下一次开发迭代

下一次迭代只做“阶段 A + 阶段 B”，不进入订单模块。

建议第一批任务顺序：

```text
1. 冻结 UTC 时间和错误码
2. 设计 Room V2
3. Android 配对页和 Keystore
4. HMAC API 客户端
5. 心跳
6. 批量上传与 ACK
7. WorkManager 离线补传
8. App 同步状态 UI
9. Debug 样本端到端测试
10. 真机局域网联调
```

该迭代完成后，系统才真正具备：

```text
微信/支付宝通知
  → Android 本地可靠保存
  → 离线队列
  → HMAC 上传
  → 服务端幂等入库
  → 管理端查看
```

这应作为进入订单、二维码和 Webhook 开发前的强制里程碑。
